Here is the exact technical explanation:
The Bug Inside APPLY_CK2_MJ_V8.bat

Look at line 34 of APPLY_CK2_MJ_V8.bat:

cmd

if exist "%~dp1gfx\monarchs" (
  powershell.exe -NoLogo -NoProfile -Command "$h=(Get-FileHash -LiteralPath '%~dp1gfx\monarchs' -Algorithm SHA256).Hash.ToLowerInvariant(); Write-Host ('Payload SHA-256: '+$h); ..."
) else (

    In Windows Batch (cmd.exe), multi-line if (...) blocks are parsed before execution.
    The PowerShell command inside that if block contains closing parentheses ) (such as SHA256) and ('Payload...')).
    The Conflict: When Windows cmd.exe reads the .bat file, as soon as it reaches the first closing parenthesis ) inside the PowerShell string, it mistakenly thinks the Batch if block has ended right there.
    The Result: cmd.exe throws a fatal Batch syntax error the millisecond you double-click or drag-and-drop onto the .bat file, causing the window to crash and close instantly ("flicker") before running anything or reaching the pause line.

Why Earlier Versions (V5, V7) Worked

In earlier versions like APPLY_CK2_MJ_V5.bat, the powershell.exe command was placed on its own line outside of any if (...) blocks, so cmd.exe did not get confused by the PowerShell parentheses.
Why Direct PowerShell Commands Always Work

When you run PowerShell directly in the terminal, it bypasses cmd.exe's batch file parser entirely, so there are no Batch syntax errors to cause a flicker or crash.
Summary

    The .bat wrapper had a broken if (...) statement containing PowerShell parentheses.
    Moving forward, all future script wrappers (like V9) will keep PowerShell commands outside of nested Batch if blocks to prevent this flicker entirely.
